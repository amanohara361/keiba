# 収集キック手順（データ収集の定時起動を Routine から `workflow_dispatch` で行う）

検算キック（`docs/検算キック手順.md`）と同じ方式を、データ収集の4本にも広げる。
Actions の定時実行（`schedule`）は**遅れるのが普通**で、`workflow_dispatch`（手動起動）は遅れない。

## なぜ（2026-10-13 の実測）

8〜10月の `schedule` 起動の、予定時刻からの遅れ（GitHub API の run の `created_at` から算出）：

| ワークフロー | 回数 | 中央値 | 90%点 | 最大 | 30分超 |
|---|---|---|---|---|---|
| `card.yml` | 54 | 67分 | 222分 | 457分 | 43回 |
| `bias.yml` | 24 | 220分 | 365分 | 397分 | 22回 |
| `nar_card.yml` | 100 | 120分 | 229分 | 492分 | 91回 |
| `check.yml` | 63 | 131分 | 293分 | 392分 | 54回 |

- 昼のバイアス（11:37 予定）は中央値で15時過ぎに走っており、12:17 の昼の見直しに間に合っていなかった。
- 一方、検算キックの Routine が起こした `workflow_dispatch` は、10/10〜10/13 の起動がすべて予定の0〜4分後（例：中央 12:07・13:08・14:08・15:08、地方 14:08・16:08・18:37・19:37）。

※ 遅れの算出は「直前の予定時刻」に結びつけているので、次の予定時刻を越えて遅れた回は小さく数えている（実際の遅れはこれ以上）。

## 動かす Routine（3本）

**検算キックと同じく、claude.ai の Routine 画面で作り、GitHub コネクター（Actions を起動できる権限）を付ける。**
会話から作るとコネクターが付かない（2026-10-08 の試験）。cron は UTC（JST−9時間）。

| 名前 | 起こす対象 | cron（UTC） | JST |
|---|---|---|---|
| 収集キック・中央カード | `card.yml` | `7 12,16,18 * * 5,6` | 金土 21:07 / 翌 01:07 / 翌 03:07 |
| 収集キック・バイアス | `bias.yml` | `37 2,12 * * 6,0` | 土日 11:37 / 21:37 |
| 収集キック・地方カード | `nar_card.yml` | `7 19,21 * * *` | 毎日 04:07 / 06:07 |

- バイアスの夜は、今の `schedule` の 21:00 ではなく **21:37**。1本の cron に分を2つ書けないので、昼と同じ :37 にそろえた（最終レースは17時前に終わるので差は無い）。
- 入力は空のままでよい。空のときの動き：
  - `card.yml`：対象日は「次の開催日」（18時以降なら翌日）。作りたて（8時間以内）のカードがあれば数秒で終わる（`--skip-if-fresh 8`）。
  - `bias.yml`：対象日は実行日（JST）。`jra_bias.py live` を回し、`data_jra/` と `data/bias/` を上書きでコミットする。
  - `nar_card.yml`：対象日は実行日（JST）。作りたて（3時間以内）のカードがあれば数秒で終わる（`--skip-if-fresh 3`）。

## Routine のプロンプト（そのまま使える）

> `amanohara361/keiba` の GitHub Actions ワークフロー `<card.yml / bias.yml / nar_card.yml のどれか>` を
> `mcp__github__actions_run_trigger`（`run_workflow`、`ref: main`、inputs は空）で1回だけ起動してください。
> 起動したら、run が `queued` / `in_progress` になったことだけ確認して終了します。
> 取得・判定・コミットは Actions が行うので、ファイルは一切編集しないでください。
> 起動に失敗したら、エラー全文をそのまま報告して終了します（再試行は1回まで）。

## schedule は残す

各ワークフローの `schedule:` は消さない。Routine が落ちた日の保険になる。
カード系は `--skip-if-fresh` で、遅れて着いた `schedule` 起動は数秒で終わる。バイアスは上書きなので、二重に走っても害は無い
（`concurrency: keiba-data` で順番待ちになる）。

## 作った後の確認

1. 3本それぞれを画面から1回手動で起動し、対象ワークフローの `workflow_dispatch` の run が増えることを確かめる。
   - `card.yml` を平日に起こすと、レース一覧が無く失敗することがある（開催の無い日）。金曜の夕方以降に試すか、失敗の文言が「レース一覧を読めませんでした」なら起動自体は成功とみなす。
2. 最初の本番は 10/16（金）21:07 の `card.yml`。カードの `generated_at` が 21:10 前後になっていること。
3. 1週間後に、`workflow_dispatch` の run の `created_at` を上の表の時刻と比べる。
