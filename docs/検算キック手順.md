# 検算キック手順（Routine から `workflow_dispatch` を叩く）

`check.yml` / `nar_check.yml` の定時（schedule）起動は、**抜けはないが5〜6時間遅れる**。
そのため発走後に着き、メールが来なかった（2026-10-08 の調査。経緯は `docs/決定ログ.md`）。
`workflow_dispatch` は遅延しないので、**時刻どおりに Routine を起こして手動起動と同じことを自動で行う**。

Routine がやるのは「起動ボタンを押す」ことだけ。検算・メールは従来どおり Actions が行う。

## 動かす Routine（3本）

**Routine には claude.ai の画面で GitHub コネクターを付ける。** 会話（`create_trigger` ツール）から作っただけだと
コネクターが付かず、起動したセッションに `mcp__github__actions_run_trigger` が無い（2026-10-08 の試験で確認。下記「試験結果」）。
画面で GitHub コネクター（Actions を起動できる権限）を付け、毎回まっさらなセッションで起動する設定にする。
cron は UTC（JST−9時間）。分は :00 を避けて :07 / :37 に揃える。

| 名前 | 起こす対象 | cron（UTC） | JST |
|---|---|---|---|
| 検算キック・中央 | `check.yml` | `7 1,4,5 * * 6,0` | 土日 10:07 / 13:07 / 14:07 |
| 検算キック・地方 昼 | `nar_check.yml` | `7 5,7 * * *` | 毎日 14:07 / 16:07 |
| 検算キック・地方 夜 | `nar_check.yml` | `37 9,10 * * *` | 毎日 18:37 / 19:37 |

※ 時刻は workflow 側の cron と同じにしてある。Routine が時刻どおりに動く間は、遅れて着く schedule 起動は
  発走済みガードで空振りする（害はない。下記「schedule は残す」）。

## Routine のプロンプト（そのまま使える）

> `amanohara361/keiba` の GitHub Actions ワークフロー `<check.yml または nar_check.yml>` を
> `mcp__github__actions_run_trigger`（`run_workflow`、`ref: main`、inputs は空）で1回だけ起動してください。
> 起動したら、run が `queued` / `in_progress` になったことだけ確認して終了します。
> 検算・印・買い目・メールは Actions が行うので、ファイルは一切編集しないでください。
> 起動に失敗したら、エラー全文をそのまま報告して終了します（再試行は1回まで）。

- 日付（`date` input）は空のまま。workflow が実行日を使う（`TZ=Asia/Tokyo`）。
- 「対象レースがあるか」は workflow 側（`nar_card.py --gate`、発走済みガード）が判断する。Routine 側では判断しない。

## schedule は残す

`check.yml` / `nar_check.yml` の `schedule:` は**消さない**。Routine が落ちた日の保険（遅れてでも1回は走る）になる。
遅れて着いても、発走済みのレースは黙って除外される（`check.yml` 冒頭のコメント）。重複メールが気になるときは、
実測して決定ログに書いたうえで schedule を間引く。

## 前提と確認が必要な点

- **Routine のセッションに GitHub Actions を叩けるコネクターが付いているか。** 画面で作ったら、必ず1回手動で起動して
  `workflow_dispatch` の run が増えることを確かめる（確認前は有効のまま放置しない）。
- コネクターが付かない場合の代替は、`data/bets/` への push で起こす方式（`check.yml` が既に対応）。
  ただし `data/bets/<日付>.json` は予想本体なので、起動専用のダミー更新を入れる設計は別途決める（未決）。
- Routine の起動そのものが数分ずれる可能性。**実測してから**「何分前倒しするか」を決める。
- 地方は `nar_check.yml` に `push:` を持たせていない（`nar_check.yml` のコメント参照）。Routine 方式は dispatch なので競合しない。

## 試験結果（2026-10-08）

1. 会話から `create_trigger` で作った Routine を `fire_trigger` で起動した。セッションは約20秒で終わり、
   `mcp__github__actions_run_trigger` を ToolSearch で2回探して見つからず、起動できなかった（`mcp_servers` が空）。
   このとき3本は無効にした（`trig_0137AJ9y9BLLcv4K5xmnUUS3` 中央 / `trig_017wrgph7ihdPSQLnAtq9Du1` 地方 昼 / `trig_01WSaDVJWfGbDqgknbBSbQ3N` 地方 夜）。
2. ユーザーが**同じ3本に画面で GitHub コネクターを付けた**（作り直しではない。旧Routineの削除は不要）。
   「地方 昼」を手動起動すると `nar_check.yml` の `workflow_dispatch` の run が増え、成功した（run #268、10:50 JST）。
   コネクターが効いていることはこれで確認できた。3本を有効に戻した。
3. 未確認：中央と地方 夜の手動起動。最初の本番確認は、地方 昼の 14:07 JST に `workflow_dispatch` の run が定時に増えること。
