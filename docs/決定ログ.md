コードを読めば分かる「何をしたか」は書かない。理由が消えると、次のセッションが

## データ取得

**netkeiba のオッズAPIは `action=update` を使う。`init` は古いキャッシュを返す。**
`jra_bias.py` のコメントに元から書いてあった。`init` で取った値は朝の
スナップショットで、直前検算の意味が消える。

**発走前は netkeiba API、発走後はスポーツナビ。判定は「発走時刻を過ぎたか」の一点。**
以前あった「確定オッズは発走から約5時間保持される」は 2026-08-02 に反証済み。
発走2.5時間後に `middle` が返った例があり、経過時間としきい値に相関がない。
時間で分岐する設計は成り立たない。

**Claude のサンドボックスは db.netkeiba.com に到達できない（403 Tunnel connection failed）。
GitHub Actions のランナーは到達できる。**
だからデータ取得は Actions 側に置く。サンドボックスで動かないコードを書いても
テストできないので、`fetcher` を差し替えられる形にしてオフラインでテストする。

**`api.github.com` はサンドボックスから遮断されているが、github.com の git
エンドポイントは通る**（`git ls-remote` は成功する）。読めるが書けない。

**地方（keiba.go.jp）はセッションから到達できる。netkeiba だけが遮断されている。**
2026-08-12 に実測。`RaceDataDownload?type=daily` が 200 / application/zip を返し、
中の CSV がそのまま読めた。`race.netkeiba.com` `db.netkeiba.com` は同じ環境で 403。
**「外部は全部 Actions 経由」と一般化していたのは誤りだった。** 遮断はホスト単位で、
確かめずに広げると、使える経路を自分で塞ぐ。

**ページ構造は推測せず、Actions の probe で実物を見る。**
サンドボックスから netkeiba に到達できないので、パーサーを手元で検証できない。
`probe` は結果を `data/probe/last.txt` にコミットするので、`git pull` して読む
（実行ログのAPIは巨大なJSONに包まれて返ってくる）。推測で正規表現をいじると
当たるまで何往復もする。2026-08-11 の調査で次が判明した。

- 馬ページは3つに分かれている。トップ（`/horse/{id}/`）には競走成績も血統も無い。
  競走成績は `/horse/result/{id}/`、血統は `/horse/ped/{id}/`。
  **`form.py` はトップから探していたため、道悪実績の照会は本番でずっと空だった。**
- 競走成績の見出しは1文字ずつ空白で割れている（「着 順」「オ ッ ズ」）。
  空白を詰めてから完全一致で引く。「馬 場」と「馬場 指数」が隣接するので、
  前方一致にすると取り違える。
- 血統表は5代分を rowspan で結合している。**rowspan の大きさが世代**なので
  それだけを使う。リンクの出現順は深さ優先で父系を潜るため、4つ目が母にならない。
- レース一覧のクラス表示アイコンは `Icon_GradePos01` が付いた方。
  **16〜18は重賞ではなくクラス（3勝・2勝・1勝）**。番号の意味を推測して
  G1/G2/G3に割り当てたため、浜名湖特別（2勝クラス）がG2に化けて
  1次スクリーニングを素通りした。知らない番号は None にする。

## 実行と配信

~~**直前検算は「規律クリア」のメールを送らない（2026-08-12 ユーザー承認済み）。**~~
~~地方は1日最大4回（14:07/16:07/18:37/19:37）検算が回るため、問題が無い日でも~~
~~「自動配信 直前検算 完了」が最大4通届き、多すぎるという指摘を受けた。~~
~~`docs/index.html`（GitHub Pages）で最新状態はいつでも見られるようになったため、~~
~~メールは「発注を止めた（BLOCK）」ときだけに絞った。~~
2026-08-13、これが裏目に出た。定時実行が最大92分遅れる仕様（下記）と
「規律クリアは無音」が重なると、メールが来ないことが「まだ実行前／遅延中」
「規律クリアで問題なし」「本当に壊れている」のどれなのか受信側で区別できず、
本当は正常に遅延して動いていただけの回を「怪しい」と誤認させてしまった。
実際に起きた流れ：14:07予定の便が92分遅れて15:39に着火→内容は規律クリア→
無音のまま→「メールが来ない、壊れているのでは」という問い合わせになった。

**直前検算はメールを毎回送るが、規律クリアの回は1行サマリにする
（2026-08-13 ユーザー承認済み）。** 完全な無音（旧方式）と、毎回フルレポート
（さらに旧方式・「多すぎる」の原因）の中間を取った。フルレポートを見たい
ときは `docs/index.html` を見ればよい。「朝の買い目が届いていません」の
警報（買い目ファイルが無い日）は今までどおり毎回フルで送る——こちらは
2026-08-01に13時間気づけなかった事象そのものの検知なので、絞らない。
実行そのものの回数（cron）は変えていない。実オッズの再取得と `docs/index.html` の
更新は毎回のまま。

**定時実行（`schedule`）は大幅に遅れる。手動実行（`workflow_dispatch`）は遅れない。**
実測で85分と119分。毎時00分は特に混む。だから直前検算は前倒しして :07 に置く。
間に合わせたい日は Actions 画面から手動実行する。

**定時実行にしか通らない枝をワークフローに作らない。**
`if: github.event.schedule != ''` で対象日を決めていたが、それだと手動実行の
テストランでその枝を通れず、本番の経路に一度も動かしたことのないコードが残る。
対象日の決定は `card.py` に持たせ、定時実行と手動実行が同じ道を通るようにした。

**終了コードは「ジョブが役目を果たせたか」で決める。**
「買い目が無い」「発注を止めた」は検知して知らせた時点で成功。これを赤にすると
買い目を出さない日が毎回赤くなり、本当の障害（SMTP断・netkeibaの構造変更）が
同じ色に埋もれる。赤は「知らせられなかった」だけに絞る。
0=正常 / 3=要確認だが通知できた / 1=知らせられなかった。

**小さく確実な出力を先にやる。**
2026-08-01、予想もExcelも07:21に完了していたのに、次のDrive投稿でパースエラーが
起きて20:30まで停止した。分析ではなく配信の一手で13時間を失った。
以来、買い目txt → JSON → Drive → Gmail の順で、倒れても手元に残る順に並べている。

**取得できなかったことを静かに「0件」と出さない。**
週次レビューは結果が1件も取れなければ終了コード3を返し、本文の先頭に警告を出す。
空の集計はいちばん危ない出力で、壊れているのに正常に見える。

**「結果が取得できない」は netkeiba 側の反映遅れであり得る。翌日に再取得すれば
直る（2026-08-18、ユーザーの指摘を受けて`review_retry.yml`を新設）。**
2026-08-17（月）の週次レビューで12レース分の結果が取得できず、警告付きで
確定してしまった。`results.py`が使う`db.netkeiba.com`の結果ページ・パース処理は、
`バイアス蓄積`（`bias.yml`）が同じ関数を使って毎週実績を出しており壊れていない
——実際、2日後に手動で同じ日付を再取得したところ12レース全て正常に取得できた。
**パースの不具合でも netkeiba のアクセス遮断でもなく、月曜09:17 JSTの時点で
netkeiba側の反映がまだ間に合っていなかっただけ**（jra_bias.pyが同日夜の実行で
「当日中はこの状態が普通」と自己申告しているのと同じ性質の遅れが、稀に翌朝まで
延びることがある、と理解するのが妥当）。
- 火曜09:17 JSTに`review_retry.yml`を追加した。月曜分のレビューに「結果を
  取得できていない」の注記があるときだけ、同じ期間で`review.py`を再実行し、
  件名に「（結果取得の再試行）」を付けてメールを再送する。注記が無ければ
  （欠けが無かった、もしくは月曜のうちに直っていた）何もしない——同じ内容の
  メールを毎週送らないため。
- 判定は`data/review/<date>.md`に既にある警告文言をgrepするだけで、
  再取得を試みる前にネットワークへ出ない（無駄な実行を避ける）。
- `review.py`に`--subject-suffix`を追加し、再試行回のメールが月曜分と
  同じ件名で来て「誤送信・重複では」と紛らわしくならないようにした。

**朝の予想セッションは Routine（定期トリガー）で起こす。GitHub Actions ではない。**
カード作成（前夜）も直前検算（昼）も週次レビュー（月曜）も無人で回るのに、
その真ん中の「印を打つ」だけが人の起動待ちだった。**鎖が一箇所でも人に戻ると、
その人が起動しなかった週は全部が止まる**（2026-08-01 の13時間と同じ形）。
印は判断なので Actions には置けず、Claude のセッションを定刻に立てる形にした
（2026-08-11 設定・土日 07:00 JST）。

**07:00 にしたのは、10:07 の「買い目が届いていません」警報より 3 時間先に置くため。**
遅れても警報より先に着く。警報が鳴ったら、それは本当に届かなかったということ。

**カードの鮮度は日時で線を引く。「ファイルがある」は根拠にならない。**
2026-08-12（水）朝に 08-15 のカードを作れてしまった。中身は全15レース（確定時36）、
頭数が出走登録ベース（26頭。JRAは最大18頭）、オッズが `status:"yoso"` の予想オッズ。
**確定前の姿でも、ファイルとしては正常に見える。** 前夜の3本が全部落ちた週に
これを掴むと、暫定データで印を打つことになる。基準は「対象日の前日18:00 JST 以降」。
定時実行は3本とも前日夜〜当日未明なのでこの線を越え、週の半ばのものは越えない。

**Routine には手順を書かず、`docs/朝タスク手順.md` を読ませる。**
毎回まっさらなセッションが立つのでプロンプトは単体で完結する必要があるが、
手順の実体をプロンプトに書くと**リポジトリの手順書と二重管理になり、必ずずれる**。
プロンプトは「正本を読め」と分担線だけを持ち、中身は手順書に置く。

**地方は毎日回す。土日固定の仕組みでは重賞を1つも拾えない。**
2026年8月の12日間で地方の重賞・準重賞は16鞍あり、その大半が平日だった
（2026-08-12 の判断）。中央が土日だけなのに引きずられて土日で設計すると、
それが丸ごと落ちる。

**Routine が起こす新しいセッションには、リポジトリを明示しないと何もクローンされない。**
2026-08-12、地方の Routine の初回が自動発火・手動発火とも空振りした。原因は
プロンプトが「CLAUDE.md を読む」から始まっていたことで、真っさらなセッションには
CLAUDE.md どころかどのリポジトリかという情報すら無かった。セッション自身は
リポジトリ名を推測して勝手に `git clone` することはせず、正直に「特定できない」と
報告して終わっており、**判断は正しかった**。直すべきはプロンプト側だった。
対策として、プロンプトの先頭に `mcp__Claude_Code_Remote__add_repo` で
`owner: amanohara361, repo: keiba` を明示するステップ0を足した（中央側の
Routine にも同じ欠陥があったため、同時に直した）。**「ファイルを読め」で始まる
プロンプトは、読む前にファイルがそこにある根拠を持たない。**

**地方の検算は「対象がある日」だけ回す。**
地方は毎日どこかで開催しているが、重賞は毎日ない。無条件に毎日回すと
「朝の買い目が届いていません」が平日ほぼ毎日鳴り、**2026-08-01 を捕まえるための
警報が意味を失う**。`nar_card.py --gate` がカードを見て3つを区別する:
`run`（対象あり）/ `none`（取得できて該当なし・無音）/ `missing`（カードが無い・要通知）。
**`none` と `missing` を同じ扱いにしない。** 混ぜると、取得が壊れている日が
「今日は無い日」に紛れる。これは「取得できなかったことを静かに0件と出さない」の
同じ話で、今度は日単位で起きる。

**`nar_card.yml` の定時実行（04:07/06:07 JST）が2本とも発火しなかった事例
（2026-08-28）。** `nar_check.yml`が「地方のカードが作れていません」と警報を出し、
`list_workflow_runs`で確認したところ、対象日のnar_card.ymlの実行記録が
（成功・失敗を問わず）**1件も存在しなかった**。ジョブが失敗したのではなく、
cronトリガー自体がGitHub側で発火していない。一方、同じ時間帯（04:56 JST・
05:44 JST）に`nar_check.yml`は通常どおり成功しており、Actions全体の障害では
ない。手動実行（workflow_dispatch）は数秒で正常に完了し、カードも問題なく
作れた（対象日は重賞・準重賞0件で、内容としては警報どおり空だった）。

**訂正（同日追記）：** 当初「concurrency group `keiba-data` の混雑で間引かれた」
という仮説を書いたが、反証が見つかった。**同じグループを共有する`nar_check.yml`が
まさに同じ時間帯（04:56 JST・05:44 JST）に問題なく発火・成功している。**
`cancel-in-progress: false`なので、混雑していても本来は「待たされて遅れて実行
記録が残る」形になるはずで、記録自体が1件も無いのはグループの混雑では説明が
つかない。

現時点で一番筋が通る説明は、**GitHub Actionsの`schedule`トリガーが公式に
「ベストエフォート」と案内されており、高負荷時は遅延どころか黙って発火しない
ことがある**という既知の制約（特に「1つのリポジトリに多数のスケジュール実行が
あると間引かれることがある」という案内あり）。このリポジトリはcronだけで
7本（card/nar_card/check/nar_check/bias/review/review_retry）動いており、
単純にこれに該当した可能性が高い。concurrency groupの中身の問題ではなく、
GitHub側のスケジューラの制約として受け止める。構造変更（concurrency groupの
分割等）はしていない。

**再訂正（同日夜追記）：「発火しなかった」ではなく「約8時間強遅れて発火した」
が正確だった。** 当日昼過ぎに`list_workflow_runs`を見直したところ、
04:07 JST枠は12:32 JST着火（8時間25分遅れ）、06:07 JST枠は14:18 JST着火
（8時間12分遅れ）で、どちらも`event: "schedule"`として実際に走っていた
（朝6時台に確認した時点ではまだ影も形も無かったため「発火自体が無い」と
誤認した）。ドキュメントに記録済みの「85〜119分の遅延」を大幅に超える
規模の遅延がGitHub側で起きていた、というのが最終的な結論。**「間引かれて
消える」ではなく「ひどく遅れて律儀に来る」**ため、`review_retry.yml`のような
「翌日に再試行する」設計は引き続き有効（8時間強の遅れなら翌朝には収束する）。

**対策として新しい仕組みは足していない。** 既存の`nar_check.yml`の警報
（カードが無ければメールで知らせる）が今回も正しく機能し、手動実行での
即時リカバリも数分で終わった。今のところ「稀に起きても安全網が拾って
すぐ手動で直せる」範囲だと判断し、再発頻度を見てから構造対応（concurrency
groupの分割など）を検討する。

**コード変更は`.py`もPRを経由させる（2026-08-28 ユーザー承認）。**
2026-08-25〜28、日次のRoutineセッションがタスク中に見つけたコードのバグ
（`bet_builder.py`のワイド複数流し二重計算、`nar_card.py`のJRA所属馬データ
上書き、`win_probabilities`移行時の書き漏らし対応など）をその場で直し、
そのまま`main`へ直接pushする状態が続いていた。「`main`直push・PR不要」は
もともと`data/`配下のデータファイル用の規約で、これをコードにまで広げたのは
各Routineセッションの自己判断であり、明文化された許可ではなかった。

実害として、`win_probabilities`移行では新項目を書かないまま朝タスクがpushし、
その日の買い目が1点も出ない事故が起きている（`朝タスク手順.md`参照）。
ノーレビューのロジック変更が即座に本番（次の定時実行）へ反映される構造
そのものがリスクだと判断し、**`data/`配下のデータファイルは従来通り直push
可、それ以外の`.py`ファイルを変更した場合はbranchを切ってPull Request
（draftでよい。mergeを待つ必要は無い）を作る**ルールを`朝タスク手順.md`・
`地方競馬手順.md`の両方に明記した。

データファイルまでPR化しなかったのは、毎日大量に生成・更新される性質上
（印付け・検算のたびにコミットが発生する）、そこまでPR化すると運用が
回らなくなるため。あくまでロジック変更（`.py`）に限定した規律。

**検算結果をMarkdownでも書き出す（2026-08-29 ユーザー依頼）。**
`data/bets/`・`data/checks/`の生JSONをGitHubのファイル閲覧画面で開くと
ただのコードとして表示され読みにくい、という指摘を受けた。`docs/index.html`
（GitHub Pages）は「最新1回分」しか見られない設計なので、過去の特定の日を
見返す用途には向かない。`data/review/`の週次レビューと同じ発想で、
`check.py`が走るたびに`data/checks_md/YYYY-MM-DD.md`へ整形済みMarkdownも
書き出すようにした（`report_md.py`を新設。中身は`report_html.py`と同じ
RaceVerdictから取るだけで、判断には関与しない）。これで過去分もGitHub上で
そのままブラウズして読めるようになる。

処理コストは軽微（テキストファイル1つの追加書き出しのみ）で、直前の
`nar_card.yml`欠落調査で判明した「GitHub側のスケジューラの詰まり」とは
無関係（個々のジョブの実行時間ではなくトリガーの発火自体が原因だったため）。

## Cowork 側の制約

**Cowork のサンドボックスはマウント先のファイルを作成・更新できるが、削除できない。**
git はコミットのたびに `.git/index.lock` を作って消すので、Cowork では git が動かない。
2026-08-08 に残ったロックを消せず `Operation not permitted` で止まった。
~~→ 朝タスクはファイルを書くだけ。commit と push は Windows 側の `github_push.bat`
（タスクスケジューラで土日 08:00 / 12:00）。認証済みの Git Credential Manager を
使うのでトークンの受け渡しも要らない。~~
**2026-08-12 に撤回。** 下の「Cowork とクラウドを完全に分離する」を見よ。

**Cowork とクラウドを完全に分離する。`github_push.bat` は廃止（2026-08-12）。**
クラウド側に地方の Routine（毎日08:00 JST）が加わったことで、同じ日の
`data/bets/YYYY-MM-DD.json` を**3つの独立した書き手**（Cowork・中央 Routine・
地方 Routine）が触りうる状態になっていた。Cowork は書く前に `git pull` しない
ので、クラウド側が先に push した内容を知らずにローカルへ書き、`github_push.bat`
の `git pull --rebase` が同じファイルの衝突を起こしうる。衝突すれば push も失敗し、
**PC 上のリポジトリが rebase 途中の壊れた状態のまま残る**（次回実行時に
`git rebase --abort` が要る）。衝突しなくても、地方 Routine が「既存の races を
消さず追記する」設計で書いた内容を、その設計を知らない Cowork の書き込みが
丸ごと上書きして消しうる。

3つの独立した書き手を git 側で調停する（Cowork にも pull・マージ判断をさせる）
のではなく、**Cowork をクラウドから完全に切り離す**方を選んだ。Cowork の出力
（買い目txt・Excel・Drive・Gmail）はPC上で完結し、GitHubには一切触れない。
クラウド側（Routine・GitHub Actions）もCowork側のファイルを一切読まない。
お互いを見ないので、衝突がそもそも起こりようがない。

失うのは「同じ日に両方が予想を作ったとき、どちらを正とするか」の自動調停
（旧: source が cowork なら上書きしない）。今後は**その日どちらを見て馬券を
買うか、人が選ぶ**運用になる。GitHub の履歴だけでは全体が見渡しにくいという
理由もあり、Cowork 側のExcel・Gmailを人間が読む窓口として引き続き使う。

`github_push.bat` はファイルごと消さず、何もせずログを書いて終わる無害な
スタブに置き換えた（PC側のタスクスケジューラ登録を消し忘れても実害が
出ないようにする多重の保険）。

**ブラウザ経由でのコミットは採らない。**
この案件は「壊れやすい自動化が止まって機会を失う」ことへの対策なので、
毎週の必須経路にブラウザ自動化を置くと、セッション切れ・UI変更・Chrome未起動で
同じ失敗に戻る。

**アプリ内タスク同士は独立した保険にならない。**
2026-08-01 は朝タスクと14:30タスクが両方止まり、20:30過ぎに一斉起動した。
本命の保険はアプリの外にある `買い目確認.bat`（Windowsタスクスケジューラ）。

## ファイル形式（Windows 側）

**`.bat` と `.ps1` は ASCII のみ。改行は CRLF。**
cmd.exe は bat を OEM コードページ（cp932）で解釈するので、BOMなしUTF-8の日本語
リテラルは解析時点で化ける。PowerShell 5.1 も BOMなし `.ps1` を同様に読む。
LF のまま保存すると `goto` のラベルが解決できず、**メッセージも出さずウィンドウが消える**。
`.py` は対象外（Python3 は UTF-8 既定）。

- 変換：`sed -i 's/\r*$/\r/' *.bat`
- 検証：`grep -c $'\r' f.bat` と `wc -l < f.bat` が一致すれば CRLF
- 検証：`grep -nP '[^\x00-\x7F]' f.ps1` が無出力なら ASCII のみ
- 括弧ブロック内の echo に `)` を書かない（ブロックが途中で閉じる）

## 沈黙する失敗をやめる（2026-08-26）

**手順が実行不能なまま走り、それが正常な見送りに見えていた。**

データを推測で埋めなかった）。問題はその後で、止まったことが誰にも伝わる

- 直前検算のレポートは、規律違反より**先に**入力欠落の見出しを出す。
- メールの件名を「【要確認】朝タスクの入力が欠けています（n件）」にし、
  終了コードも `EXIT_NEEDS_ATTENTION` にした。

## push トリガーと手動起動の二重発火事故（2026-09-05）

再作成したJRA Routineが2026-09-05夜に初めて自然発火し、`data/bets/2026-09-06.json`

アクセスできていたこと（2026-09-05に作り直した際の「connectorsパラメータが

`git pull --rebase --autostash`が衝突して失敗した。

main側の状態は一貫していることを確認済み）。ただし repeated に起きれば

`trig_018G6dzEEpJo821Da7W8SG51`）のプロンプトも、次回発火までに同じ内容へ
`update_trigger`で更新する。

**教訓**：「ツールにアクセスできない」という推測は、実際にRoutineを
動かして確認するまで確定情報として扱わない。今回はRoutine作成時の

一切使えない」と判断したが、それは`create_trigger`というAPI呼び出し1つの
制約であり、実際にfireしたRoutineセッションが持つツール一式とは別物

## `fire_trigger`で強制起動したRoutineはpushできないことがある（2026-09-08）

新設した週次検証タスクRoutine（`trig_01XVs7Z2sXfLK6iDk8ysYShk`）を、当週分の
バックログを先取りさせる目的で`fire_trigger`を使い手動起動したところ、その
セッションは「Home directoryにCLAUDE.mdが無いのでリポジトリ未アタッチ」と
判断し、`add_repo`系ツールが使えないままread-onlyの`git clone`にフォール
バックした。分析自体は最後まで完走しコミットも作成したが、書き込み権限が
無いため`git push`が403で失敗し、「このコンテナが破棄されると、この
コミットは失われる」と自己申告して終了した。実際にコンテナは破棄され、
コミットは失われた（`検証ノート.md`の該当エントリは、このセッション自身が
`review.py`の`collect()`を再実行して手動で書き直した）。

**同型の障害は今回が初めてではない。** JRA朝タスクのRoutineでも一度、同じ
「add_repo未実行→read-only clone」パターンが起きている（そのときは
`interrupt_session`で対処した）。つまりこれは単発の事故ではなく、
**`fire_trigger`による強制起動は、自然なcron発火と同じ権限セットアップを
保証しない**という、再現性のある構造的な穴だと判断する。

ストランドしたセッションからの回収も試したが道が無かった：`SendMessage`で
セッションID（`session_01MBnXkkwUdToDR3rGevhFWe`）宛てに送ろうとしたが
「No agent named '...' is reachable」で失敗し、`ListAgents`も"No reachable
agents"を返した。`get_session`では`connection_status: connected`
`session_status: IDLE`と生きて見えるにもかかわらず、兄弟セッションから
メッセージを送る経路が無い。**forceで起動したCCRセッションは、生きていても
ピアメッセージングでは呼びかけられない。**

**対応方針**：pushを伴うRoutine（`data/`・`検証ノート.md`等への書き込みが
最終ゴールのもの）は、バックログの先取りや動作確認の目的であっても
`fire_trigger`で強制起動しない。自然なcron発火だけを信頼する。どうしても
早めに結果が欲しい場合は、`fire_trigger`で走らせるのではなく、このセッション
（cloud側の対話セッション）で同じロジックを直接再実行して手で反映する方が、
「消えるかもしれないコミット」を作ってしまうより確実。
週次検証タスクの次回の自然発火（2026-09-15 10:00 JST）で、push込みで
問題なく完走するかを確認すること。

## `nar_check.yml`のpushトリガーを撤去（2026-09-08）

2026-09-08、地方競馬の朝タスクRoutineが戸塚記念（川崎11R）の印を
`data/bets/**`へpushしたところ、`check.yml`（直前検算）と`nar_check.yml`
（地方の直前検算）が**同じpushイベントに対して同時に起動**し、両方とも
同じ`data/checks/2026-09-09.json`を新規作成しようとした。地方側が先に
commit・pushに成功し、JRA側が`git pull --rebase`した時点でadd/add
コンフリクトになりpushだけ失敗した（check.py自体は最後まで走り、メール
送信は成功していたので実害は無し。ジョブが赤くなっただけ）。

両ワークフローとも`concurrency: group: keiba-data`は入れてあり
（2026-09-05の「push トリガーと手動起動の二重発火事故」で対策済み）、
これは同一ワークフロー内の複数トリガー（push＋手動起動）は直列化できて
いた。しかし今回は**別々のワークフローファイルが同じpushイベントに
ほぼ同時に反応するケース**で、concurrencyグループのロックが競合を
防ぎきれなかった。

**原因を辿ると、そもそも`nar_check.yml`にpushトリガーを持たせる必要が
無かった。** 両方が呼んでいる`check.py`はJRA/地方の区別をせず、
`data/bets/`にある全レースをまとめて計算する。つまり`check.yml`の
pushトリガー1つで、JRA・地方どちらのRoutineが`data/bets/`をpushした
場合でも「印付け直後の即時検算」は既に全レース分カバーできていた。
`nar_check.yml`側のpushトリガーは2026-09-05の修正（PR #47）で
`check.yml`と同じ理由づけをそのまま複製して追加したものだが、
`nar_check.yml`固有の存在意義（ナイター向けの遅い時間帯のスケジュール
実行、`nar_card.py --gate`による該当日フィルタ）とは無関係で、実際には
「重賞がある日にだけ`check.yml`と丸ごと重複した2回目の計算を走らせる」
だけの効果しかなかった。

**対応**：`nar_check.yml`から`push:`トリガーを削除。スケジュール実行
（14:07/16:07/18:37/19:37 JST）とworkflow_dispatchは維持する。
`check.yml`のpushトリガーが引き続きJRA・地方どちらのpushにも即時反応
するため、機能の欠落は無い。リトライやコンフリクト解消ロジックを足す
のではなく、**そもそも同じ仕事を2つのワークフローにやらせない**ことで
競合そのものを無くす方針を選んだ（`docs/決定ログ.md`の他の箇所とも
一貫する「衝突する余地を無くす」というやり方）。

## pushトリガー起因の「問題なし」メールを黙らせる（2026-09-09）

ユーザーから「直前検算のメールが来た時刻を並べたら、最後に来るのが大体
深夜になっている」と指摘された。実例（Gmail検索結果）では、戸塚記念
（川崎11R）だけで同日中に「直前検算 問題なし」が08:15/18:37/21:17/22:51/
23:47の5通、9/6のJRAレース群でも17:36/18:18/18:20/20:37/22:04/22:47の
6通届いていた。

**原因**：`check.yml`の`push`トリガー（`data/bets/**`、2026-09-05追加）が、
朝タスクRoutineが印を打つたびに、あるいは直前検算自身が実オッズで買い目を
確定して`data/bets/`に書き戻すたびに発火する。`check.py`は「問題なし」の
回も**必ず**1行メールを送る設計（2026-08-13、定時実行の遅延と「壊れて
いるのでは」という誤認を防ぐため意図的にそう作った）。この設計は1日数回・
時刻が決まっている定時実行では正しいが、pushトリガーは1日に何度も、
しかも深夜まで連続して起きうるため、同じ「問題なし」が積み重なるだけの
通知になっていた。

**対応**：`check.py`に`--quiet-if-clean`を追加。「問題なし」のときだけ
メール送信を省略し（ログ・保存・HTML/MDの書き出しはこれまでどおり行う）、
発注を止めた／入力欠落のメールはこのフラグの影響を受けず通常どおり即時に
送る。`check.yml`の「検算を実行」ステップで`github.event_name == 'push'`
のときだけこのフラグを渡すようにした（`nar_check.yml`は直前のpush
トリガー撤去で対象外）。

これで、定時実行（10:07/13:07/14:07 JST）の「問題なし」ハートビートは
従来どおり届き続ける一方、印付けの都度発火するpushトリガーからの重複
メールは止まる。要確認の事象を握りつぶす方向の変更ではなく、**同じ
「問題なし」を何度も送るだけの通知だけ**を止めた。

## scheduleの大幅遅延で深夜に固まる「問題なし」も黙らせる（2026-09-09）

上のPR #53を実装した直後、ユーザーから「本当にこれで直ったのか、深夜の
メールは実際に何がトリガーだったのか」と問われ、Actions APIで1件ずつ
`created_at`とイベント種別を突き合わせ直した。結果、スクリーンショットの
時刻のうち**push起因だったのは朝の2件（08:15・08:18）だけ**で、深夜に
固まっていた分（17:36〜23:47）は全部`event: schedule`だった。

`nar_check.yml`の定時実行は本来14:07/16:07/18:37/19:37 JSTの4回のはず
だが、実際にジョブが動いた時刻は18:37/21:17/22:51/23:47と、後ろになる
ほどズレが酷くなって（最大4〜5時間遅れ）深夜に固まっていた。ジョブの
ステップ内訳を見ると「起動が要求されてから実際にジョブが走り出すまで」は
2秒以内で、**このリポジトリのワークフロー側の詰まりではなく、GitHub
Actions側の定時起動そのものが数時間単位で遅れていた**（check.ymlの
コメントに元からある「定時実行は大幅に遅れる」問題の、より酷いケース）。

つまりPR #53の`--quiet-if-clean`（push起因のときだけ黙る）は正しい修正
だったが、この日の深夜メールの主因はカバーしていなかった。ユーザーに
その旨を訂正して伝え、対策の方向性を確認した：「遅すぎる回は問題なし
メールを黙らせる」を選んだ（cronの前倒しなどGitHub側の遅延を軽減する
方向は見送り、効果が読めないため）。

**対応**：`check.py`に`_all_races_already_started(verdicts)`を追加。
対象日の全レースが発走済み（＝review_sheet()が`meta={'skipped': ...}`
を付けたレースだけ）なら、トリガー種別（push/schedule）にかかわらず
「問題なし」メールを送らない。1鞍でもまだ発走前のレースが残っていれば
これまでどおり送る（2026-08-13の教訓——遅延と規律クリアの区別がつかなく
なる——を壊さないため、「今日はもう何も確認できることが無い」場合に限定
した）。テスト2件追加（全レース発走済みなら黙ること／1鞍でも発走前が
残っていれば従来どおり送ること）。326件全件成功。
