# 朝タスク手順（クラウド版・方針B）

土日の朝、クラウドのセッションがこの手順で買い目を作る。
**PCの起動に依存しない経路**であり、Cowork の朝タスクを置き換えることを目指す。

このセッションは **Routine（定期トリガー）が土日 07:00 JST に自動で起こす**。
人が起動しなくてよい（下の「自動起動」を参照）。

Cowork 側は2026-08-12に完全分離した。Cowork の出力（買い目txt・Excel・
Drive・Gmail）はPC上で完結し、GitHubには触れない。このセッションもCowork
のファイルを一切読まない。同じ日に両方が予想を作ることはあるが、
自動的な優先順位は無い。**どちらを見て購入するかは人が都度判断する。**
経緯は `docs/決定ログ.md` を参照。

---

## 自動起動（Routine）

`card.yml` が前夜にカードを用意し、`check.py` が昼に検算する。
その間の**印を打つ一手だけが人の起動待ちだった**ので、そこに定期トリガーを置いた。

| 項目 | 値 |
|---|---|
| 名前 | `競馬 朝の予想（土日 07:00 JST）` |
| cron | `0 22 * * 5,6`（UTC。金土 22:00 UTC ＝ 土日 07:00 JST） |
| 起動の仕方 | 毎回**新しいセッション**を立てる（前回の文脈を持ち越さない） |
| 通知 | 完了時にプッシュ通知 |

**毎回まっさらなセッションで起きる**ので、渡すプロンプトは単体で完結していなければ
ならない。実物は下の「自動起動プロンプト」。手順の正本はこのファイルなので、
プロンプトは「このファイルを読め」と言うだけにして、内容を二重に持たない。
**手順を変えるときはこのファイルを直す。プロンプトは触らなくてよい。**

**このセッションはメールを送らない。** 配信は 10:07 / 13:07 / 14:07 の直前検算が
やる。Routine 側は完了時のプッシュ通知だけを出す。

**カードの鮮度は「対象日の前日18:00 JST 以降に作られたか」で見る。**
定時実行は3本とも前日夜〜当日未明なので、この線を越える。越えないカードは
**週の半ばに手で作った暫定カード**であり、出馬表が確定する前の姿をしている。
2026-08-12（水）朝に 08-15 のカードを作って実測したところ、全15レース
（確定時は36）、頭数が出走登録ベース（26頭。JRAは最大18頭）、
オッズが `status: "yoso"`（予想オッズ）だった。**「ファイルがある」だけでは
使ってよい根拠にならない。**

**カードが無ければ何もできない。** netkeiba にはクラウドのセッションからも
到達できない（egress ポリシーで 403。Cowork だけの制約ではない）ので、
自分で取得する道は無い。そのため `card.yml` に 03:07 JST の3本目を足して、
前夜の2本が両方落ちた日をそこで拾う。前夜に成功していれば `--skip-if-fresh` で
数秒で終わる。

07:00 にしたのは、10:07 JST の直前検算（「朝の買い目が届いていません」の警報）
までに 3 時間の余裕を取るため。定時実行が遅れても警報より先に着く。

止めたい・時刻を変えたいときは、セッションで「朝の予想の Routine を止めて」と
頼めばよい（`list_triggers` → `update_trigger` / `delete_trigger`）。
Actions のワークフローではないので、GitHub の画面には出てこない。

**プロンプトの先頭にリポジトリを明示するステップ0が要る。** 2026-08-12、地方側の
Routine でこれが無かったため初回が空振りした（自動発火・手動発火とも、真っさらな
セッションがどのリポジトリか分からず何もできずに終わった）。同じ欠陥がこちらにも
あったため同時に直した。詳しくは `docs/決定ログ.md`。

### 自動起動プロンプト

```text
土日の朝の予想タスク。自動起動なので人は見ていない。判断は自分で完結させること。

0. **まずリポジトリを用意する。** 新しいセッションには何もクローンされていない。
   ホームディレクトリに CLAUDE.md が読めなければ、まだアタッチされていない証拠。
   `mcp__Claude_Code_Remote__add_repo` を owner: "amanohara361", repo: "keiba",
   access: "push" で呼び、返ってきた clone コマンドを実行し、
   `mcp__Claude_Code_Remote__register_repo_root` で登録してから、
   そのディレクトリに cd してから先へ進む。
   add_repo が使えない場合のみ `git clone https://github.com/amanohara361/keiba.git`
   で読み取りだけ確保し、push できないことを最後の報告に明記する。
   **リポジトリ名を推測して他を clone しない。** 分からなければ「リポジトリを
   特定できない」とだけ報告して終わる。

1. CLAUDE.md / docs/決定ログ.md / docs/朝タスク手順.md を読む。
   **手順の正本は docs/朝タスク手順.md**。以下と食い違ったらそちらに従う。
2. 現在時刻を確定する（CLAUDE.md「現在時刻の確定」）。
   確定時刻より後に発走するレースだけを対象にする。
3. 今日 JRA の開催が無ければ、何もせず終わる。
4. data/cards/YYYY-MM-DD.json を読む。無い・日付違い・**generated_at が対象日の
   前日18:00 JST より前**（＝週の半ばに作った暫定カード）の場合:
   - GitHub Actions を起こせるツール（actions_run_trigger）が使えるなら
     workflow: card.yml, ref: main, inputs.date: 対象日 で起こし、
     終わったら git pull して読む。人に頼まない。
   - 使えないなら **買い目を作らずに終わる**。「カードが無い」とだけ報告する。
     netkeiba にはこのセッションから到達できない（egress ポリシーで 403）。
     自分で取得しようとしない。10:07 の直前検算が警報を出す。
5. races[].candidate が true のレースに予想メソッドの7ステップを適用して印を打つ
   （**candidate はレース直下。screening の下ではない**）。
   screening.excluded が埋まっているレースは対象外。
   **各印に、根拠になった手順の番号を steps に付ける**（例: `{"mark":"◎",
   "umaban":7,"steps":[1,3,5]}`）。後ろ向き研究のための仕込みで、任意項目
   だが手間は小さいので必ず付けること。形式は data/bets/README.md。
   印を打たなかったが分析シート上でプラス材料があった馬は `partners`
   （馬番＋短い理由）に残す（第13章「相手の広げ方」の候補プール）。
6. **買い目（bets）と勝負度（confidence）は書かない。**
   2026-08-14〜、実オッズが確定してから（直前検算）組む方式にした
   （朝時点は暫定オッズしか無く、規律の基準が仮の値になってしまうため）。
   `marks`・`partners`・`subjective_hit_rate` までを出せば朝タスクの仕事は終わり。
   **数を揃えない。**◎が絞れない・相手候補も無いレースは印だけ記録してよい。
7. data/bets/YYYY-MM-DD.json を書く（形式は data/bets/README.md、source は "cloud"）。
   start_time・subjective_hit_rate を必ず入れる。
8. python make_bets.py --show で形式が契約に合っているか確認する
   （この時点で bets は空でよい）。
9. git add data/bets/ && git commit && git push origin main で **main に直接**
   コミットする。check.yml は main を読むので、ブランチに置くと 10:07 の検算に
   届かない。**PR は作らない。**
10. **push した直後に、actions_run_trigger で check.yml を1回手動起動する**
    （workflow: check.yml, ref: main, inputs: {no_email: true}）。
    2026-08-14〜、買い目の組み立ては直前検算（bet_builder）が実オッズで行う
    方式にしたため、10:07の定時実行より前に発走するレース（10:20発走の
    早いレースなど）は、定時実行を待っていると間に合わない。定時実行は
    大幅に遅れることがある（85〜119分の遅延を実測済み）ため、
    「10:07の3時間後」ではなく「10:07に運悪く発走してしまう」レースが
    実際に発生した（2026-08-15、中京2R 3歳未勝利が発走までに一度も
    評価されずBLOCKになった）。**手動起動（workflow_dispatch）は定時実行と
    違って遅延しない**（数秒で始まる）ので、印を打ち終えた直後にこの1回を
    挟むことで、朝の時点で市場が開いている（＝オッズが取れる）レースは
    その場で買い目まで確定する。以降は10:07/13:07/14:07の定時実行が
    通常どおり実オッズで組み直していく。`no_email: true` にするのは、
    この1回はメール通知が目的ではなく買い目を早く確定させるための
    ものだから（通知は定時実行に任せる）。

制約:
- Cowork はもう data/bets/ に書かない（2026-08-12に分離済み）ので、
  他ソースとの上書き判定は不要。自分が書いた "cloud" をそのまま更新してよい。
- 予想メソッド.md・検証ノート.md・CLAUDE.md は編集しない（承認制）。
- 厩舎コメント・パトロールビデオ・競馬新聞の印は取れない。取れない情報は
  無いものとして判断し、note に「直前タスクで要確認」と残す。推測で埋めない。
- 10:07 JST の直前検算より前に push を終える。

最後に、対象レース数・印・中穴候補・見送った理由を3〜5行で報告する。
```

## 前提：なぜこの形なのか

netkeiba に到達できるのは GitHub Actions のランナーだけで、Claude の
サンドボックスからは 403 で弾かれる。一方、印を打つ判断ができるのは Claude だけ。
そこで**取得と判断を分け、リポジトリのファイルを受け渡し場所にする**。

```
GitHub Actions（card.yml）        このセッション                GitHub Actions（check.py）
netkeiba に到達できる              netkeiba に到達できない        実オッズに到達できる
判断しない（取得のみ）             印を判断する・買い目は組まない  判断しない（算術のみ）
↓                                 ↓                             ↓
data/cards/YYYY-MM-DD.json ─読む→ data/bets/YYYY-MM-DD.json ─読む→ 実オッズで bets・confidence を確定
                                  （marks・partners まで）        ↓
                                                          data/bets/YYYY-MM-DD.json へ書き戻す
```

分担線は予想メソッド 第14章がすでに引いている。1次スクリーニング
（機械的な絞り込み）が Actions、2次選別（7ステップ本分析）がこのセッション。

## 手順

### 1. 現在時刻を確定する（最優先）

CLAUDE.md「現在時刻の確定」に従う。**確定した現在時刻が対象レースの発走時刻を
過ぎていたら、そのレースの買い目は作らない。** 全レース発走済みなら
「遅延により実行不可」と報告して終わる。

このセッションは毎回新しいコンテナで起動するので、Cowork で起きた
「システム時計が起動時刻で凍結する」事象は構造的に起こらない。
それでも、外部ソース（`data/cards/` の `generated_at` など）と突き合わせる。

### 2. リポジトリを最新にする

```bash
git pull origin main
```

メソッド系のファイル（`CLAUDE.md` `予想メソッド.md` `検証ノート.md`）は
**keiba-repo 側が正**。作業前に必ず pull する。

### 3. カードを確認する

`data/cards/YYYY-MM-DD.json` は**前夜のうちに出来ている**（金・土の 21:07 JST に
`card.yml` が走る。落ちたときのために 01:07 JST にもう1本）。
通常はそのまま読めばよく、起動を待つ必要はない。

カードに**馬体重と馬場状態は入っていない**。馬体重は発走の約60分前まで
発表されないので朝に取り直しても入らず、そこは 13:07 / 14:07 の直前検算が見る。
朝の判断は近走・血統・馬場別実績・前夜のオッズで行い、馬体重と馬場が効く論点は
note に「直前タスクで要確認」と書いて残す。

カードが無い・日付が違う・`generated_at` が**対象日の前日18:00 JST より前**の
場合だけ、自分で起こす。定時実行は3本とも前日夜〜当日未明なのでこの線を越える。
越えないカードは週の半ばに作った暫定カードで、出馬表が確定する前の姿をしている
（実測：全15レース／確定時36、頭数が出走登録ベースで26頭、オッズが `yoso`）。
**「ファイルがある」だけでは使ってよい根拠にならない。**

```
actions_run_trigger  workflow_id: card.yml, method: run_workflow,
                     ref: main, inputs: {date: YYYY-MM-DD}
```

**手動実行は数秒で始まる**（定時実行の85分・119分の遅れは手動には出ない）。
所要は候補6レースで20〜30分。終わったら `git pull` してカードを読む。
人に頼む必要はない。

### 4. 2次選別（7ステップ本分析）

カードの `races[].screening.excluded` が埋まっているレースは対象外。
`candidate: true` のレースについて、予想メソッドの7ステップをフル適用する。

カードに入っている事実：

| 項目 | 使う章 |
|---|---|
| `entries[].recent`（直近5走：着順・距離・馬場・通過順・上がり・騎手・馬体重） | 第2章 減点方式、第8章 7つの視点、第9章 条件好転 |
| `entries[].going_record`（馬場状態別の着別度数） | 第5章、第10章 |
| `entries[].pedigree`（父・母・母父） | 第5章 ダート適性、第12章 |
| `entries[].weight` / `weight_diff` | 第12章 |
| `odds.win_odds` / `odds.ninki` | 第8章 狙うオッズ帯、第13章 |
| `conditions`（馬場・天候・コース） | 第1章、第10章 |
| `data_jra/` の実測バイアス | 第10章、第11章 |

**カードに無いものは「要確認」と書く。推測で埋めない**（第12章）。
特に、厩舎コメント（第1章手順2）とパトロールビデオ（第9章）はこの経路では取れない。
そこが埋まらないことを理由に印を曖昧にせず、**取れない情報は無いものとして
判断し、その旨を note に残す**。

### 5. 印を打ち、中穴候補を残す（買い目は組まない）

**2026-08-14〜、印は朝タスクが確定するが、買い目（bets）と勝負度（confidence）は
直前検算が実オッズで組み立てる方式にした。** 朝時点は実オッズが出そろって
いないことが多く、暫定オッズで買い目まで固めると第13章の基準（合成オッズ・
期待値）が仮の値になってしまう（詳細は予想メソッド第13章「印と買い目組み立て
の分離」、経緯は決定ログ参照）。
この作業に関しては、レベルの高いモデルを、高い思考モデルで使う。ここが中核だからだ。

朝タスクがここで出すのは：
- `marks`：7ステップを適用した◎○▲△
- `partners`：印は打たなかったが分析シート上でプラス材料があった馬
  （馬番＋短い理由。第13章「相手の広げ方」の候補プール）
- `subjective_hit_rate`：主観的中率

**数を揃えない**（第14章）。◎が絞れないレースは印だけ記録してよい。

### 6. 買い目JSONを書いてコミットする

`data/bets/YYYY-MM-DD.json`（形式は `data/bets/README.md`）。
必ず入れる項目：`start_time`・`subjective_hit_rate`。`bets`・`confidence` は
書かない（書いても直前検算が上書きする）。
`source` は `"cloud"` にする（Cowork 版と区別して、あとで精度を比較するため）。

```bash
python make_bets.py --show      # 形式が契約に合っているか確認できる（betsは空でよい）
git add data/bets/ && git commit -m "買い目: YYYY-MM-DD" && git push origin main
```

**このセッションは git を実行できる。** Cowork のサンドボックスと違って
ファイルの削除ができるので、`.git/index.lock` の問題は起きない。

### 7. 直前検算に引き継ぐ

朝タスクの仕事はここまで。13:07 / 14:07 の直前検算（`check.py`→
`bet_builder.py`）が実オッズで `bets`・`confidence` を確定し、第13章の規律を
あてたうえで結果をメールする。朝タスクはこの結果を待たない。

## この経路が倒れたときの保険

- 買い目JSONが無ければ、直前検算が「朝の買い目が届いていません」と警報を出す
  （2026-08-01に13時間だれも気づかなかった事象を検知するのがこれ）
- Cowork の朝タスクが動いていれば、そちらの買い目が先に入る
- どちらも無ければ、`make_bets.py --paste` で手で作れる

## まだこの経路でできないこと

- **厩舎コメント**（第1章 手順2）… 取得先が定まっていない
- **パトロールビデオ**（第9章）… 映像の確認はどうやってもできない
- **競馬新聞の印との照合**（第1章 手順7）… 同上
- **Excel への記録**（2026_予想ログ.xlsx・成績管理.xlsx）… PC側の作業。
  クラウド側は `data/bets/` と週次レビューで仮想成績を持ち、
  Excel は実際に購入した分を持つ、と役割を分ける
