# spot-predict: 単発レースのオンデマンド予想

## なぜこのスキルがあるか

このシステムの自動化（`card.yml`・「朝の予想」Routine・`check.yml`）は
**土日のJRA**と**毎日のNAR**を前提に組まれている。年に数回しかない
海外重賞や、祝日・台風による振替開催のような「土日ではないJRA開催日」は、
このcronの外側にある。

自動検知（祝日カレンダーを持たせて毎日チェックする等）を検討したが、
見送った。理由：
- JRAの出馬表は通常レース4〜5日前に公開される。仮にcronを毎日に広げても、
  `card.py`の`target_day()`は「次の開催日」を機械的に拾うため、開催日が
  何日も先だとまだ出馬表が無い状態でカードを作ろうとして中途半端な
  取得になる（現状の土日運用は「前夜に確実に出馬表が揃っている」ことに
  依存した設計）。
- 祝日開催・振替開催は年に数回で、JRAの年間開催カレンダーで事前に分かる。
  そのために常時稼働のcron監視を持たせるコストは見合わない。
- 海外重賞も同様に年に数回で、そもそも`card.py`は netkeiba（中央）専用の
  スクレイパーであり、海外レースのデータソースは無い。

そのため、**「気づいた人（ユーザー）が投げたら動く」ほうが、頻度の割に
安く確実**という判断（2026-09-22、ユーザー承認）。実際、2026-09-22の
中山・台風延期振替（火曜開催）は、このスキルを作る前から同じ手順
（`card.yml`をworkflow_dispatchで手動起動→7ステップで印付け→push）で
すでに一度うまく回っている。このスキルはその場しのぎの手順を再現可能な
形に固定しただけで、新しい仕組みを作ったわけではない。

## 対象の見分け方

1. **中央（JRA）のレースで、対象日が土日ではない**（祝日・振替開催・
   平日の特別開催など）→ 下記「A. JRA単発開催」。
2. **海外のレース**（凱旋門賞・ブリーダーズカップ・ドバイワールドカップ・
   ロイヤルアスコット等）→ 下記「B. 海外レース」。
3. 対象日が土日のJRA、または任意の日のNARなら、**このスキルは使わない**。
   既存のRoutineが自動で処理する（すでに今日〜数日以内に印が付いているはず。
   無ければRoutineの不具合なのでユーザーに報告する）。

迷ったら、まず`data/bets/{対象日}.json`と`data/cards/{対象日}.json`が
既に存在するか確認する。両方あれば自動化がすでに拾っている可能性が高い。

## A. JRA単発開催（祝日・振替開催）

既存のパイプラインをそのまま使う。**新しいコードは不要。**

1. **現在時刻を確定する**（CLAUDE.md「現在時刻の確定」の手順）。対象レースの
   発走時刻を過ぎていないか必ず確認する。

2. **カードが無ければ`card.yml`を手動起動する。**
   `mcp__github__actions_run_trigger`（`method: run_workflow`）で
   `workflow_id: "card.yml"`, `ref: "main"`,
   `inputs: {"date": "YYYY-MM-DD"}` を渡す。workflow_dispatchは定時実行と
   違い遅延しない（数秒〜数十秒で終わる）。終わったら
   `mcp__github__actions_list`（`list_workflow_runs`）で完了を確認し、
   `git pull origin main`する。
   - すでに`data/cards/{date}.json`があり新しければこの手順は不要。

3. **`data/cards/{date}.json`を読み、`予想メソッド.md`の7ステップで
   候補レースに印を打つ。** CLAUDE.mdの指示どおり、印付け本体は
   Agentツールで`model: "opus"`のサブエージェントに行わせる
   （`予想に関してはmodelはopusをhighで使う`）。渡す情報はカードの
   出走馬データ一式と、可能なら`予想メソッド.md`の該当章。
   `marks`・`partners`・`win_probabilities`まで埋める。**`bets`・
   `confidence`は書かない**（直前検算が実オッズで確定する。書き方の
   詳細は`data/bets/README.md`）。

4. **`data/bets/{date}.json`に追記する。** 既にその日のファイルが
   あれば`races`を消さずに追記。`org`は`"jra"`（既定なので省略可）、
   `source`は`"claude-adhoc"`のように分かる値にしておく。
   `python make_bets.py --show`で形式を確認してから、
   `git add data/bets/ data/cards/ && git commit && git push origin main`
   で**mainに直接**コミットする（PRは不要。データファイルのみ）。

5. **pushした時点で`check.yml`が自動発火する**（`data/bets/**`への
   push トリガーが既にある）。発走前なら実オッズで`bets`・`confidence`
   が確定しメールが届く。追加の操作は不要。

6. ユーザーには対象レース・印・簡単な根拠を報告する。

## B. 海外レース

こちらは`card.py`のようなデータ取得パイプラインが存在しない
（netkeiba専用スクレイパーのため）。**`data/bets/`の自動パイプラインには
書き込まない**（`bet_builder.py`・`discipline.py`はJRA/NARの実オッズ
API・公式CSVを前提にしており、海外ブックメーカーのオッズには対応
していない。無理に`org`を追加して流用すると、存在しない前提で
的中率・合成オッズを計算することになり事故のもと）。

1. **現在時刻とレースの発走時刻（現地時間→JST換算）を確定する。**
   海外レースは深夜〜早朝JSTになることが多い。

2. **WebSearchで出走馬・枠順・近走成績・馬場想定・オッズの論調を集める。**
   このセッションからは`race.netkeiba.com`等ほぼ全ドメインが
   `EGRESS_BLOCKED`でWebFetch不可（2026-09-20実測）。WebSearchの
   検索結果スニペットだけで集められる範囲でよい。取れなかった情報は
   無理に埋めず「要確認」と明記する。

3. **Agentツールで`model: "opus"`のサブエージェントに7ステップの
   印付けをさせる。** 渡す情報は集めた出走馬情報・馬場想定・
   （分かれば）市場オッズ傾向。海外レースは第5章・第6章（ダート・
   夏競馬）等、日本特有の章は基本適用外である点に注意。

4. **出力はチャットで直接ユーザーに返す**（◎○▲△と根拠、券種の
   考え方）。`data/bets/`への自動反映はしない。ユーザーが記録として
   残したいと言えば、`検証ノート.md`か別ファイルへの手動記録を提案する
   （このスキルの必須範囲には含めない）。

5. 情報が薄く7ステップが成立しない場合は、無理に印を絞らず
   「情報不足でここまでしか判断できない」と正直に報告する
   （CLAUDE.mdの「推測で埋めない」原則）。

## 共通の注意

- **予想メソッド.md・検証ノート.md・CLAUDE.mdはこのスキルの中で編集しない。**
  Aの手順で予想メソッドの各章を参照するのは読むだけであり、書き換えは
  別途承認が要る（既存のルールと同じ）。
- `.py`のコードは変更しない。バグに気づいたら報告に留める。
- Bで的中率や期待値の数字を出す場合も、JRA/NARの規律（合成オッズ3.0倍・
  期待値1.2等）をそのまま海外レースに適用してよいという意味ではない。
  海外の控除率・オッズ体系は国・ブックメーカーごとに異なるため、
  数字は参考値として提示し、断定的な規律判定はしない。
