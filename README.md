# 競馬予想 — クラウド運用

予想メソッド 第13章「買い目の規律」を GitHub Actions 上で**定刻に**機械適用する。

## なぜこれを作るのか

検証ノートの運用4週間の集計:

| 指標 | 数値 |
|---|---|
| ◎の複勝率 | **62.5%**（直近2週は7鞍中4鞍が1着） |
| 全体の回収率 | **48.4%** |
| 「◎が3着以内なのに買い目が全不的中」 | **5件** |

検証ノート自身の結論は「**外れの原因は馬選びではなく買い目設計に偏在している**」。
印は既に機能していて、失っているのは買い目設計の側だった。
そして買い目設計は算術と規則で書ける。**このリポジトリはそこだけを担当する。**

印を打つ判断には一切関与しない。

## 何を検出するか

各チェックは、実際に起きた損失に対応している。

| チェック | 対応する事例 |
|---|---|
| **印と買い目の矛盾**（第13章F案） | 2026-08-02 クイーンS。○を外し▲（8着）を残して回収0円。的中は馬連7-11=1,120円 |
| **相手1頭固定の馬連・馬単** | 2026-07-26 東海S。○の2着抜けで全滅 |
| **印馬だけの3連複** | 2026-07-25 関ケ原S / 07-26 関屋記念 / 07-19 函館2歳S |
| **単勝の推奨レンジ**（第8章 4.0〜9.9倍） | 2026-08-02 アイビスSD。確定3.8倍・期待値1.10 |
| **合成オッズ3.0倍・期待値1.2**（第13章） | 2026-07-25 キングジョージ。推定オッズで誤判定 |
| **発走済みガード** | 2026-08-01。◎2鞍とも1着だが配信が発走後で購入不可 |
| **朝の買い目が届いていない** | 2026-08-01。13時間だれも気づかなかった |

検証ノートに記録された買い目構成ミスは、**予想ミス1件を除いて全て機械で弾ける**。

## 動くもの

| ワークフロー | 実行タイミング | 中身 |
|---|---|---|
| `直前検算` (`check.yml`) | 土日 **11:00 / 14:30 JST** | 実オッズを取り直して第13章の規律を適用 → メール |
| `テスト` (`test.yml`) | push / PR ごと | ネット接続なしで検証 |

11:00は「朝の買い目が届いているか」の早期確認、14:30が本番の直前検算。
重賞は15:25〜15:45発走が多いので、Actions の遅延（通常5〜30分）を見込んでも間に合う。

## 分担

```
Cowork（朝）                GitHub Actions（定刻）
──────────────              ────────────────────────
7ステップで印を打つ      →   data/bets/YYYY-MM-DD.json
主観的中率を見積もる          ↓
勝負度を判定                 実オッズを取り直す（netkeiba API・action=update）
                             合成オッズ = 1 ÷ Σ(1/o)
                             第13章の規律をあてる
                             発走済みガード
                             ↓
                             メール送信 ＋ data/checks/ に記録
```

**判断（人間とClaude）と算術（機械）を分ける。** 算術は遅刻もハングもしない。

朝の買い目が届いていなければ、**それ自体を警報としてメールする**。
2026-08-01に鳴るべきだったのがこの警報。

## 朝タスク側でやること

`data/bets/YYYY-MM-DD.json` を1つコミットする。形式は
[`data/bets/README.md`](data/bets/README.md) を参照。

既に書いている `買い目_YYYYMMDD.txt` と内容は同じで、機械が読める形にしただけ。
txt はフェイルセーフとして引き続き書く（`買い目確認.bat` が読む唯一の経路）。

## 初期設定

### 1. Secrets を登録

Settings → Secrets and variables → Actions

| 名前 | 値 | 必須 |
|---|---|---|
| `SENDER_EMAIL` | 送信元 Gmail アドレス | ✅ |
| `SENDER_PASSWORD` | Gmail の**アプリパスワード** | ✅ |
| `RECEIVER_EMAIL` | 受信先 | ✅ |
| `SMTP_SERVER` | 既定 `smtp.gmail.com` | |
| `SMTP_PORT` | 既定 `587`（`465` なら SSL） | |

### 2. Actions に書き込み権限

Settings → Actions → General → Workflow permissions → **Read and write permissions**

### 3. 動作確認

`data/bets/` にサンプルを置いて、Actions →「直前検算」→ Run workflow。

## 手元で動かす

```bash
python check.py --no-email                              # 今日の買い目を検算
python check.py --date 2026-08-02 --now 2026-08-02T14:30 --no-email
pytest                                                  # テスト（ネット接続不要）
```

外部ライブラリのインストールは不要（`jra_bias.py` と同じく標準ライブラリのみ）。
CI で依存インストールが失敗して定刻を落とす、という事故も起きない。

## ファイル構成

```

bets.py          買い目データの契約（スキーマ）と読み書き
odds.py          実オッズ取得（netkeiba API・action=update）
discipline.py    第13章の規律 ← 基準を変えるのはここ
mailer.py        メール送信

jra_bias.py      トラックバイアス判定（既存・手つかず）
nar_csv.py       地方競馬のCSV解析（既存・手つかず）
予想メソッド.md   ★メソッド本体。承認なしに編集しない
検証ノート.md     ★学習ログ
CLAUDE.md        運用ルール
```

## 今後

- **第2段階**: `jra_bias.py fetch` を Actions で回して `data_jra/` を蓄積する。
  **Actions は db.netkeiba.com に到達できる**ので、CLAUDE.md にあるスポーツナビの
  手動保存運用が不要になる。「100レース貯まれば精度が上がる」が放置で達成される（現在12レース）。
- **第3段階**: 印そのものを Claude API で生成する。`bets.py` の契約を満たせば
  検算側は無変更で繋がる。ただし第9章の映像確認（パトロールビデオ）はどうやってもできない。

## 注意

- 基準値（合成オッズ3.0倍・期待値1.2・単勝4.0〜9.9倍）は**検証で承認されるまで変更しない**。
  緩和案はサンプル10件到達時に再検討する、と第13章が定めている（現在3件）。
- netkeiba の構造変更で取得に失敗した場合、オッズは「暫定」扱いになり警告が出る。
  黙って通過することはない。
