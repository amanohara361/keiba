# 競馬予想 — クラウド運用

予想メソッド 第13章「買い目の規律」を GitHub Actions 上で**定刻に**機械適用する。

## なぜこれを作るのか

検証ノートの運用4週間の集計:

| 指標 | 数値 |
|---|---|
| ◎の複勝率 | **62.5%**（直近2週は7鞍中4鞍が1着） |
| 全体の回収率 | **48.4%** |
| 「◎が3着以内なのに買い目が全不的中」 | **5件** |

検証ノート自身の結論は「**外れの原因は馬選びではなく買い目設計に偏在している**」。
印は既に機能していて、失っているのは買い目設計の側だった。
そして買い目設計は算術と規則で書ける。**このリポジトリはそこだけを担当する。**

印を打つ判断には一切関与しない。

## 何を検出するか

各チェックは、実際に起きた損失に対応している。

| チェック | 対応する事例 |
|---|---|
| **印と買い目の矛盾**（第13章F案） | 2026-08-02 クイーンS。○を外し▲（8着）を残して回収0円。的中は馬連7-11=1,120円 |
| **相手1頭固定の馬連・馬単** | 2026-07-26 東海S。○の2着抜けで全滅 |
| **印馬だけの3連複** | 2026-07-25 関ケ原S / 07-26 関屋記念 / 07-19 函館2歳S |
| **単勝の推奨レンジ**（第8章 4.0〜9.9倍） | 2026-08-02 アイビスSD。確定3.8倍・期待値1.10 |
| **合成オッズ3.0倍・期待値1.2**（第13章） | 2026-07-25 キングジョージ。推定オッズで誤判定 |
| **発走済みガード** | 2026-08-01。◎2鞍とも1着だが配信が発走後で購入不可 |
| **朝の買い目が届いていない** | 2026-08-01。13時間だれも気づかなかった |

検証ノートに記録された買い目構成ミスは、**予想ミス1件を除いて全て機械で弾ける**。

## 動くもの

| 動くもの | 実行タイミング | 中身 |
|---|---|---|
| `カード作成` (`card.yml`) | 金土 **21:07 JST**（予備 01:07 / 03:07） | 中央の出馬表・近走・血統・オッズを集めて `data/cards/` に置く |
| **朝の予想**（Routine） | 土日 **07:00 JST** | セッションを自動で起こし、カードを読んで印を打つ → `data/bets/` |
| `直前検算` (`check.yml`) | 土日 **10:07 / 13:07 / 14:07 JST** | 実オッズを取り直して第13章の規律を適用 → メール |
| `地方カード作成` (`nar_card.yml`) | **毎日 04:07 JST**（予備 06:07） | 地方の重賞・準重賞を公式CSVから集めて `data/cards/nar/` に置く |
| **地方の予想**（Routine） | **毎日 08:00 JST** | 対象がある日だけ印を打つ → `data/bets/`（`org: "nar"`） |
| `地方の直前検算` (`nar_check.yml`) | **毎日 14:07 / 16:07 / 18:37 / 19:37 JST** | 対象がある日だけ回す。ナイターの発走に合わせて夜まで → メール |
| `バイアス蓄積` (`bias.yml`) | 土日 **21:00 JST** | 結果を取って `data_jra/` に貯める |
| `週次レビュー` (`review.yml`) | 月 **09:17 JST** | 着順と払戻を突き合わせて数字を出す → メール（中央・地方をまとめて） |
| `テスト` (`test.yml`) | push / PR ごと | ネット接続なしで検証 |

**「朝の予想」だけが GitHub Actions ではない。** 印を打つのは判断なので Claude の
セッションが要る。定期トリガー（Routine）が土日の朝にセッションを自動で起こす
仕組みで、GitHub の Actions 画面には出てこない。中身は
[`docs/朝タスク手順.md`](docs/朝タスク手順.md#自動起動routine)。

**地方は毎日走る。** 中央は土日しか開催しないが、地方は毎日どこかでやっていて
**重賞も平日に組まれる**（2026年8月の12日間で重賞・準重賞16鞍、大半が平日）。
土日固定の仕組みでは1鞍も拾えない。ただし重賞が毎日あるわけではないので、
`nar_check.yml` は `nar_card.py --gate` でその日の対象を見て、
**ある日だけ**検算を回す。無条件に回すと「買い目が届いていません」の警報が
平日ほぼ毎日鳴り、意味を失うため。詳しくは
[`docs/地方競馬手順.md`](docs/地方競馬手順.md)。

10:07は「朝の買い目が届いているか」の早期確認、13:07と14:07が直前検算。
重賞は15:25〜15:45発走が多い。定時実行は**大幅に遅れる**（2026-08-08 に85分、
翌日は119分の遅延を実測）ので、前倒ししたうえで毎時00分を避けている。
確実に間に合わせたいときは Actions 画面から手動実行する（`workflow_dispatch` は遅れない）。

## 分担

```
Claude のセッション（朝）    GitHub Actions（定刻）
──────────────              ────────────────────────
7ステップで印を打つ      →   data/bets/YYYY-MM-DD.json
主観的中率を見積もる          ↓
勝負度を判定                 実オッズを取り直す（netkeiba API・action=update）
                             合成オッズ = 1 ÷ Σ(1/o)
                             第13章の規律をあてる
                             発走済みガード
                             ↓
                             メール送信 ＋ data/checks/ に記録
```

**判断（人間とClaude）と算術（機械）を分ける。** 算術は遅刻もハングもしない。

朝の買い目が届いていなければ、**それ自体を警報としてメールする**。
2026-08-01に鳴るべきだったのがこの警報。

## 朝タスク側でやること

`data/bets/YYYY-MM-DD.json` を1つコミットする。形式は
[`data/bets/README.md`](data/bets/README.md) を参照。

既に書いている `買い目_YYYYMMDD.txt` と内容は同じで、機械が読める形にしただけ。
txt はフェイルセーフとして引き続き書く（`買い目確認.bat` が読む唯一の経路）。

## 初期設定

### 1. Secrets を登録

Settings → Secrets and variables → Actions

| 名前 | 値 | 必須 |
|---|---|---|
| `SENDER_EMAIL` | 送信元 Gmail アドレス | ✅ |
| `SENDER_PASSWORD` | Gmail の**アプリパスワード** | ✅ |
| `RECEIVER_EMAIL` | 受信先 | ✅ |
| `SMTP_SERVER` | 既定 `smtp.gmail.com` | |
| `SMTP_PORT` | 既定 `587`（`465` なら SSL） | |

### 2. Actions に書き込み権限

Settings → Actions → General → Workflow permissions → **Read and write permissions**

### 3. 動作確認

`data/bets/` にサンプルを置いて、Actions →「直前検算」→ Run workflow。

## 手元で動かす

```bash
python check.py --no-email                              # 今日の買い目を検算
python check.py --date 2026-08-02 --now 2026-08-02T14:30 --no-email
python review.py --end 2026-08-09                       # 週次レビュー（メールなし）
pytest                                                  # テスト（ネット接続不要）

python nar.py calendar                                  # 今月の地方重賞の予定
python nar_card.py                                      # 今日の地方カードを作る
python nar_card.py --gate                               # 今日は対象があるか（run/none/missing）
```

`nar.py` と `nar_card.py` は**手元からそのまま動く**。地方の公式データは
keiba.go.jp にあり、netkeiba と違ってサンドボックスから到達できる。

外部ライブラリのインストールは不要（`jra_bias.py` と同じく標準ライブラリのみ）。
CI で依存インストールが失敗して定刻を落とす、という事故も起きない。

## 週次レビューが出す数字

月曜に `data/review/YYYY-MM-DD.md` を書き、要約をメールする。
**数えるだけで、反省文は書かない。** 総括は人（と Claude）が書いて 検証ノート.md へ移す。

いちばん上に出るのが「規律は収支に効いたか」で、次の2つを並べる。

- **仮想成績** … 朝の買い目をそのまま全部買った場合
- **規律適用後** … 直前検算が BLOCK したレースを除いた場合（＝実運用）

この差額が、第13章の規律を守る価値そのもの。マイナスが続くなら基準が厳しすぎる。

そのすぐ下に「配当の偏り」を置く。**回収率は少数の高配当に引っ張られやすい**ので、
的中の配当の中央値・最小〜最大・上位1件／3件を除いた回収率を並べて出す
（賭け金は減らさず、除外分の払戻だけを引く）。ここも判定はせず数字だけ
（2026-08-12追加）。

不的中は2つに分ける。混ぜると反省の向きを間違えるため。

- **買い目構成ミス** … 買い目は全外れだが、◎が3着以内 または 印が2頭以上3着以内。馬は見えていた
- **予想ミス** … 印そのものが外れた

しきい値カウンタは通算10件でメソッド見直しを検討する（第13章）。
`◎一極集中で全滅` だけは**まだ規律に入っていない候補**で、件数だけ数えている。
2026-08-08 のエルムSがこの形だった（買い目が全て◎絡みで、◎が飛んで全滅。
○は2着・△は1着だった）。現行の `lone_partner` は相手の広さしか見ないので検知できない。

## 朝タスクのクラウド化（方針B）

netkeiba に到達できるのは Actions のランナーだけで、印を打つ判断ができるのは
Claude だけ。そこで**取得と判断を分け、リポジトリのファイルを受け渡し場所にする**。

```
GitHub Actions（card.yml）        Claude のセッション
netkeiba に到達できる              netkeiba に到達できない
判断しない                         判断する
↓                                 ↓
data/cards/YYYY-MM-DD.json ─読む→ data/bets/YYYY-MM-DD.json
```

分担線は予想メソッド 第14章がそのまま使える。1次スクリーニングは
「出馬表・クラス・頭数・オッズの概況のみで**機械的に**候補を絞り込む」と
条文になっており、除外条件（2歳新馬・障害）も優先度の上下も書いてある。
2次選別（7ステップ本分析）は判断なので機械は手を出さない。

カードは**前夜のうちに定時実行で出来ている**ので、朝に誰かが起動する必要はない。
定時実行の遅れ（85分・119分を実測）が問題になるのは直前検算のような時刻の
決まった処理だけで、前夜なら2時間遅れてもその晩のうちに終わる。
馬体重は発走の約60分前まで出ないため朝に取り直しても入らず、
馬体重と馬場状態は直前検算が見る。だからカードは前夜で足りる。

手順は `docs/朝タスク手順.md`。2026-08-09 のデータで通しの動作を確認済みで、
1次スクリーニングが選んだ候補は、その日に実際に買ったレースと一致した。

そのセッションは **Routine が土日 07:00 JST に自動で起こす**（2026-08-11 に設定）。
これで前夜のカード作成から月曜のレビューまで、**人の起動を挟まずに一周する**。

## 自動になっていないもの

**メソッドの改訂は自動化しない。** 週次レビューは数えるだけで反省文を書かない
（`review.py` の冒頭に理由がある）。`予想メソッド.md` は承認なしに編集せず、
`◎一極集中で全滅` のような改訂候補は件数だけ数え、10件たまったら人が判断する。
基準値もサンプル10件までは変えない。**規律を機械が緩められる設計にしない**のが
このリポジトリの前提で、そこは意図的に手動のまま残している。

## 地方競馬（フェーズ2）

予想メソッド 第14章「フェーズ2の標準データ基盤」が定めた三層構造を実装したもの。
中央とは前提が逆を向いている。

```
中央（netkeiba）                地方（keiba.go.jp 公式CSV）
Actions だけが到達できる          セッションからも到達できる（実測200）
HTML をパースする                 CSVがそのまま降ってくる
クラスはアイコン番号から推測        競走種類名称に「重賞」と書いてある
1頭3ページ × 1.5秒               1頭0回（出馬表CSVに血統も成績も入っている）
土日                             毎日。重賞も平日にある
昼〜夕方の発走                    16:30〜21:00台（ナイター）
```

**同じリポジトリに入れている。** `予想メソッド.md` は第11章と第14章に地方の
条文を既に持ち、第13章の規律・買い目の契約・週次レビューは中央とまったく同じ
コードが通る。別リポにすると `予想メソッド.md` と `検証ノート.md` が2か所になり、
それは 2026-08-07 に `data_jra/` を20レース分失ったのと同じ形になる。

拾うのは**重賞・準重賞だけ**。特別まで広げると1日16鞍になり、地方向けの
1次スクリーニング基準を新設する話になる（重賞が回り始めてからの拡張）。

交流重賞（JpnI/II/III）には中央馬が出る。**その馬の近走は地方のCSVに1走も無い**
のが正常で、`belongs_jra` で判別して「休み明け」と読み違えないようにしてある。

## 今後

- **第2段階**: `jra_bias.py fetch` を Actions で回して `data_jra/` を蓄積する。
  **Actions は db.netkeiba.com に到達できる**ので、CLAUDE.md にあるスポーツナビの
  手動保存運用が不要になる。「100レース貯まれば精度が上がる」が放置で達成される（現在12レース）。
  → `bias.yml` で稼働中。
- **地方の拡張**: 特別戦への拡大（地方向けの1次スクリーニング基準が要る）、
  `nar_csv.py` のトラックバイアス判定を `data/cards/nar/` に繋ぐこと。
  第11章の手順は南関東4場＋園田（ハロンタイム収録場）でフル適用できる。
  交流重賞の中央馬の近走はnetkeiba馬名検索で解決済み（2026-08-13）。
- **第3段階**: 印そのものを Claude API で生成する。いまは Routine が Claude の
  セッションを起こす形で自動化しており、`bets.py` の契約を満たしている限り
  どちらに置き換えても検算側は無変更で繋がる。
  ただし第9章の映像確認（パトロールビデオ）はどうやってもできない。

## 注意

- 基準値（合成オッズ3.0倍・期待値1.2・単勝4.0〜9.9倍）は**検証で承認されるまで変更しない**。
  緩和案はサンプル10件到達時に再検討する、と第13章が定めている（現在3件）。
- netkeiba の構造変更で取得に失敗した場合、オッズは「暫定」扱いになり警告が出る。
  黙って通過することはない。
